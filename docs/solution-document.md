# Solution document — Connected Vehicle Intelligence

*Hackathon: Motorq Connected Vehicle Intelligence (open-ended). All data is synthetic.* Evidence links point to files in this repository; where something was
not verified it is said so.

## 1. Problem
Fleet operators receive a continuous stream of telemetry (position, speed, engine and battery signals, trouble codes, driver behaviour) from tens of thousands of vehicles
but need timely *decisions*: which vehicles are about to fail, which drivers are unsafe, where fuel is wasted, and what to do next — with data isolated per customer,
auditable, and cheap enough to run at 100,000-vehicle scale (≥ 100K events/s, 3× bursts, alerts < 5 s, API p95 < 200 ms).

## 2. Target users
| user | needs | served by |
|---|---|---|
| Fleet manager | what is wrong now, what to do, cost impact | dashboard, alerts with recommended actions, AI copilot |
| Maintenance planner | who to service first within workshop capacity | ML risk ranking, knapsack plan tool |
| Safety/compliance officer | risky drivers, audit trail, privacy | driver risk, hash-chained audit, location masking, erasure |
| Analyst | trends, utilisation, energy/fuel | analytics page, Parquet/DuckDB history |
| Platform/SRE | reliability, observability | health probes, Prometheus/Grafana/Loki/Jaeger, chaos tests |
| Tenant admin | accounts, GDPR requests | RBAC, erasure workflow |

## 3. Proposed solution
An event-driven platform: devices → edge → Kafka → validation → stateful stream processing → polyglot stores → API/UI/agent, with batch ML scoring and lifecycle jobs.
Differentiators: **effectively-once effects** under at-least-once delivery, **database-enforced multi-tenancy (RLS)**, **explainable** health/risk scores, an **agent that only speaks from tool output**,
and **evidence-backed** performance/SQL/security claims (generated by scripts, not typed).

## 4. Architecture
See [architecture.md](architecture.md) (system diagram, service table, sequence diagrams for ingestion and alerting) and [ai-agent.md](ai-agent.md) (agent sequence).
Services: ingestion-edge, validator, stream-processor, lifecycle, API+agent, simulator, frontend; shared library `cvi`. Decisions: ADR-001…005.

## 5. Data pipeline
[data-flow.md](data-flow.md): topics `telemetry.raw → telemetry.validated → (stream processor) → alerts`, DLQ with reasons, batch of 500, step order that makes any crash recoverable,
idempotency mechanism per side effect, event-time handling (`103,101,102` ⇒ processed as 101,102,103; late beyond 300 s excluded from aggregates), back-pressure and replay.

## 6. Database design
[database.md](database.md): 3NF relational schema with composite tenant-consistency FKs, RLS, migrations, indexes, keyset pagination, materialised views; MongoDB (raw events), Redis (state/aggregates),
Parquet (warm/cold), pgvector (knowledge/incidents). SQL evidence with real `EXPLAIN ANALYZE`: [sql-before-after.md](performance/sql-before-after.md)
(alert feed 243.8 → 0.4 ms; KPI trend 583.8 → < 0.05 ms; top-risk 277 s → 92 ms; N+1 42.9 → 1.6 ms) on 100,000 vehicles / 1,000,000 alerts.

## 7. Algorithms
[algorithms.md](algorithms.md): dedupe (Redis gate + Bloom), event-time sliding windows, EWMA z-score, Count-Min Sketch, Space-Saving Top-K, geohash/geofence, Dijkstra/A*, knapsack DP, VIN validation,
OBD-II parsing, rule/penalty scoring, hashed n-gram embeddings — each with problem, algorithm, rationale, time/space complexity, alternative and reason for the choice.

## 8. Machine learning
[ml.md](ml.md): predictive-maintenance gradient boosting on 14 features, trained on **synthetic** data, evaluated against a service-interval baseline on an untouched test split
(ROC-AUC 0.853 vs 0.596; PR-AUC 0.503 vs 0.154; precision@top-10% 0.50 vs 0.18). Versioned artifacts, local explanations, batch scoring of 100,000 vehicles. The numbers
demonstrate the method on a known synthetic structure, not real-world accuracy.

## 9. AI agent
[ai-agent.md](ai-agent.md), [ADR-004](adr/ADR-004-ai-agent-architecture.md): 14 typed tools over live data, deterministic intent→tool planner, permission and schema checks, grounded answers,
optional LLM narration with a numeric grounding check, confirmation for writes, hash-chained audit trail, rate limiting, prompt-injection screening; works with no LLM.

## 10. Security
[security.md](security.md), [STRIDE](security/stride-threat-model.md), [scan results](security/scan-results.md): JWT/OIDC, RBAC, RLS + composite FKs, rate limiting, headers/CORS, bcrypt, audit chains,
secrets management, masking, erasure, container hardening. OWASP API Top-10 mapping included. Gaps listed (device mTLS, MFA).

## 11. Scalability
[scaling.md](scaling.md): partition-by-VIN, consumer groups (48 partitions in the cloud profile), HPA/KEDA on lag, caching, keyset pagination, cold analytics off OLTP, hot-spot analysis.
Measured per-replica throughput and a clearly labelled capacity model: [benchmarks.md](performance/benchmarks.md).

## 12. CAP / PACELC decisions
[architecture.md §6](architecture.md#6-cap--pacelc-classification): billing/ownership/access control/audit/alerts → **CP, strong (PC/EC)**; raw telemetry, latest state, real-time aggregates,
rollups, vector search → **AP, eventual (PA/EL)** with idempotency as the reconciliation mechanism.

## 13. Data lifecycle
[ADR-005](adr/ADR-005-data-lifecycle.md): HOT (Redis + Mongo 7 d TTL) → WARM (hourly Parquet, tenant/date/hour) → COLD (daily compacted, zstd, IA/Glacier lifecycle rules, 730 d) → deletion; partitioning, compaction,
cost reasoning, GDPR/DPDP erasure across all tiers (tested).

## 14. Performance
[benchmarks.md](performance/benchmarks.md) (generated from `benchmarks/results/*.json`): simulator 79.5K msg/s/process (213K with 4); validator 32K msg/s/process; stream processor 4.5K events/s/process
(real Redis + PostgreSQL) with exactly-once aggregate check; API p95 29–91 ms / p99 64–119 ms at 16 concurrent clients; alerts 0.8–1.8 s after injection. **The 100K events/s end-to-end run was not
executed**; the document separates measured, theoretical and cloud (not run) numbers.

## 19. Trade-offs
* Python micro-batch consumer instead of Flink — simpler to run and test, lower per-core throughput, scale-out by partitions (ADR-003).
* Deterministic planner instead of an LLM tool loop — reproducible and safe, narrower language coverage (ADR-004).
* Hashed n-gram embeddings instead of a neural model — offline and deterministic, lexical only.
* In-process detector windows — cheap, lost on restart (re-warm).
* Shared image/package for all services — one codebase, one test suite; less isolation than per-service repositories.
* MongoDB for a week of raw telemetry — operational overhead vs keeping OLTP free of firehose I/O.
* RLS + application filters (belt and braces) — small query overhead, strong isolation.
* Keyset pagination only — no random page jumps.

## 20. Future work

OIDC (Cognito/Entra) integration with MFA; cloud load test at 100K–300K events/s and soak test; tenant self-service administration.
